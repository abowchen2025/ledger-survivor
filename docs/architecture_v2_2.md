## 1. 專案定義

### 1.1 一句話

以「週」為關卡、以「月」為賽季的個人記帳網頁：每週在花費上限內存活就得分，月底依成績換取獎勵，把省錢變成可以打的遊戲。

### 1.2 命名

| 項目 | 內容 |
|---|---|
| 中文名 | 記帳生存遊戲 |
| 英文代號 | Ledger Survivor |
| Repo | `ledger-survivor`（private）|

### 1.3 使用情境

單人使用。主要在**手機**上每日記帳（1～3 筆／天，每筆 10 秒內完成），週末或月底在電腦上看報表與結算。兩個設計後果：介面手機優先並做成 PWA；記一筆花費的操作路徑少於三次點擊。

### 1.4 核心價值主張

市面記帳 App 多數的問題是「記了但不會改變行為」。本系統的差異化在三點：
1. **週為單位**，回饋週期短到足以修正行為（月為單位時，月中超支已經來不及）
2. **遊戲化計分**，把「省下來」變成可累積的成就
3. **獎勵金來自真實省下的錢**，不憑空產生預算

## 3. 時間規則（關鍵設計決策）

### 3.1 週的定義與跨月歸屬

**規則：週一為一週之始，一週完整歸屬於「該週週四所在的月份」。**

這是 ISO 8601 對「週屬於哪一年」的規則，套用到月。效果：

- 一週永遠只屬於一個月，不切割、不按比例分攤
- 一週七天裡有四天以上落在哪個月，就歸那個月
- 例：2026/9/28（一）～10/4（日），週四是 10/1，整週歸 **10 月第 1 週**
- 例：2026/8/31（一）～9/6（日），週四 9/3，歸 9 月第 1 週

**為什麼不切在月底**：切割會產生 1～3 天的殘週，殘週的上限要按比例算、分數要另訂規則，且得分容易被少數幾筆消費放大或稀釋，破壞遊戲公平性。

**每月週數**：4 或 5 週，由規則自動算出，月可支配金額依此分配到各週。

### 3.2 時區

固定 `Asia/Taipei`。所有日期以本地日曆日存 `DATE` 型別，不用 timestamp，避開時區換算問題。

### 3.3 補登

允許補登過去任何日期的花費；已結算的週即時重算分數。不設「忘記記帳」懲罰，避免使用者為了保分而不補登真實花費。

## 4. 功能範圍

### 4.1 收入與可支配金額

| 項目 | 說明 |
|---|---|
| 月薪 | 每月一筆，預設沿用上月 |
| 額外收入 | 獎金、年終等，可多筆 |
| 固定支出 | 房租、保險、訂閱等，設定一次每月自動帶入（可設起訖月）|
| 分期月付 | 由 4.2 自動加總 |
| 儲蓄目標 | 每月固定先扣，預設 0 |

```
月可支配 = 月薪 + 額外收入 − 固定支出 − 分期月付 − 儲蓄目標
週上限預設 = 月可支配 ÷ 該月週數
```

### 4.2 信用卡與分期

**信用卡主檔**：卡名、銀行、末四碼、結帳日、繳款日、卡面顏色、**期初未付卡債**（見 4.6.4）。**不存完整卡號。**

繳款月份偏移（`due_month_offset`）由系統推算：繳款日 ≤ 結帳日 → 次月（如結帳 27 日、繳款 15 日）；繳款日 > 結帳日 → 同月（如結帳 1 日、繳款 20 日）。允許手動覆寫，但預設不需要人填。

**分期記錄**：品項、所屬卡、**消費日**、總金額、總期數、已繳期數、每期金額（自動算，可覆寫處理尾差）。**首期繳款月由系統依 4.6.3 規則推算，不由人填**，只在銀行實際帳單不同時允許覆寫並要求填原因。系統自動產出剩餘期數、剩餘金額、預計結束月、各月分期負擔曲線。分期月付計入月可支配的扣項，**不再重複記為每日花費**；分期消費本身不建 `expenses` 記錄，但在消費當週的週檢視顯示一列「本週新增分期承諾」資訊（不計分）。支援提前清償。

### 4.3 花費記錄

| 欄位 | 必填 | 說明 |
|---|---|---|
| 日期 | ✅ | 預設今天 |
| 金額 | ✅ | 支援負數（退款），不可為零 |
| 品項 | ✅ | 自由文字，提供最近輸入的快速選項 |
| 分類 | ✅ | 見第 6 節 |
| 支付方式 | ✅ | 現金／信用卡／行動支付／轉帳 |
| 信用卡 | 條件 | 支付方式為信用卡（或行動支付綁卡）時必選 |
| 備註 | — | |

**兩條規則**：
- 「獎勵」分類的花費照常記錄但**不計入週花費**（見 5.4）
- 信用卡消費以**消費日**計入週花費（控制行為的是花錢當下）；另提供「本月信用卡待繳」視圖依結帳日彙總實際現金流

### 4.4 週上限

- 預設由 4.1 公式算出
- 可逐週覆寫（例如朋友生日），需填原因；月報顯示本月調整了幾次
- 該週結束即鎖定，不可回頭改（防事後補救保分）

### 4.5 主要畫面

| 頁面 | 內容 |
|---|---|
| 本週（首頁）| 剩餘額度大字、HP 條、快速記帳、本週逐日花費 |
| 月曆 | 以週為列，每格顯示當日花費合計 |
| 分期與現金流 | 各卡分期清單、剩餘負擔、結束月時間軸；本月各卡應繳（已出帳／未出帳）；未來 6 個月現金流預估 |
| 月結 | 月分數、等級、獎勵金、各週得分、圖表 |
| 分析 | **新增**，見第 6.4 節 |
| 設定 | 收入、固定支出、儲蓄目標、信用卡、分類、獎勵分流比例 |

### 4.6 兩個時鐘：行為時鐘與現金時鐘

#### 4.6.1 為什麼要分

信用卡消費有兩個日期：花錢的那天，和錢真正離開帳戶的那天。9/23 刷 3,000，行為上是 9 月第 4 週的決定，現金上是 10/27 才出帳。兩個都是真的，回答的是不同問題：

| | 行為時鐘 | 現金時鐘 |
|---|---|---|
| 依據 | 消費日 | 繳款日 |
| 回答 | 我這週花太多了嗎 | 這個月帳戶要準備多少錢 |
| 驅動 | 週花費、HP、計分、獎勵、分類分析 | 分期月付扣項、本月應繳、現金流預估 |
| 會計類比 | 權責基礎 | 現金基礎 |

**兩個時鐘各自獨立運作，永不合併、永不互相覆蓋。** 遊戲機制只看行為時鐘；現金流功能只看現金時鐘。使用者在畫面上永遠知道自己看的是哪一個。

#### 4.6.2 各支付方式的現金時鐘

| 支付方式 | 現金離開帳戶的時間 |
|---|---|
| 現金 | 消費日 |
| 轉帳 | 消費日 |
| 行動支付（儲值）| 消費日 |
| 行動支付（綁信用卡）| 依所綁卡片的帳單規則 |
| 信用卡一次付清 | 依 4.6.3 落入的帳單 → 繳款日 |
| 信用卡分期 | 首期依 4.6.3，之後每月同一繳款日 |

#### 4.6.3 帳單歸屬與繳款月推算規則

```
消費日 d（月 m、日 dd），卡片結帳日 s，繳款月偏移 o（0 同月／1 次月）

帳單月 B = m        若 dd ≤ s
         = m + 1    若 dd > s
繳款月 P = B + o
```

範例（結帳 27 日、繳款 15 日 → o = 1）：

| 消費日 | 帳單月 | 繳款月 | 說明 |
|---|---|---|---|
| 9/23 | 9 月 | 10 月 | 你舉的例子：分期首期 10 月 |
| 9/28 | 10 月 | 11 月 | 結帳日後一天刷，多延一個月 |
| 12/30 | 1 月（次年）| 2 月（次年）| 跨年 |

範例（結帳 1 日、繳款 20 日 → o = 0）：

| 消費日 | 帳單月 | 繳款月 |
|---|---|---|
| 9/1 | 9 月 | 9 月 |
| 9/2 | 10 月 | 10 月 |

**已知不精確處**：消費日與銀行入帳日通常差 1～3 天，結帳日前一兩天的消費可能入帳晚而落到下期帳單。初版不建模這個延遲；使用者可在分期記錄上覆寫首期月、在一次付清消費上不提供覆寫（金額小、影響一個月、穩態下抵銷）。若日後發現偏差頻繁，再加卡片層級的「入帳延遲天數」欄位。

**月底日處理**：結帳日設 31 但該月只有 30 天時，視為該月最後一天。

#### 4.6.4 期初未付卡債

啟用系統的第一個月，帳戶要付的是**啟用前幾個月的卡費**，那些消費從未進過系統。不處理的話，前一到兩個月的現金流會被嚴重高估。

每張卡在建立時可填兩個金額（皆可為 0）：

| 欄位 | 說明 | 落入哪個月 |
|---|---|---|
| 已出帳未繳 | 上期帳單金額 | 最近一個尚未到的繳款日所在月 |
| 未出帳 | 本期已刷未結帳金額 | 下一個結帳日對應的繳款月 |

這兩筆只影響現金時鐘，不影響行為時鐘（不計週花費、不計分、不進分類分析）。進入穩態後欄位保留但不再有作用。

#### 4.6.5 現金流功能的範圍界線

| 做 | 不做 |
|---|---|
| 首期繳款月自動推算 | 自動抓銀行帳單 |
| 本月各卡應繳金額，區分已出帳／未出帳 | 帳戶餘額即時追蹤 |
| 未來 6 個月現金流預估（固定支出 + 各卡應繳 + 儲蓄目標 vs 月收入）| 對帳自動化 |
| 期初未付卡債設定 | 循環利息、最低應繳、遲繳罰息 |
| 現金流缺口月份標示 | 多幣別 |

#### 4.6.6 對 4.1 公式的釐清

4.1 的「分期月付」明確定義為：**繳款月 = 該月的所有分期期款總和**（現金時鐘），不是「本月有進行中分期的期款總和」。兩者在分期首月與末月會差一期。

## 5. 遊戲規則 v1

> 規則版本獨立編號。分數由 API 即時計算不落庫，改規則不必回溯改資料。

### 5.1 名詞

週上限 T、週花費 E（不含「獎勵」分類）、週餘額 R = T − E、餘額率 r = R ÷ T。
「存活」：R ≥ 0；「超支」：R < 0。

### 5.2 週計分

| 項目 | 規則 | 分數 |
|---|---|---|
| 存活分 | R ≥ 0 | +10 |
| 餘額率分 | 每 10% 餘額率得 2 分 | 最高 +10 |
| 豐收加分 | r ≥ 30% | +5 |
| | r ≥ 50%（取高者，不疊加）| +10 |
| 連勝加乘 | 連續存活第 2 週起每週 | +3，最高 +9 |
| 超支 | 基礎 | −5 |
| | 超支率每 10% 再扣 | −2，單週最低 −15 |
| | 連勝歸零 | |

週最高 39 分，最低 −15 分。

### 5.3 月結等級

平均週分 = 月總分 ÷ 該月週數

| 等級 | 平均週分 | 稱號 |
|---|---|---|
| S | ≥ 28 | 生存大師 |
| A | ≥ 20 | 老練倖存者 |
| B | ≥ 12 | 撐過來了 |
| C | ≥ 0 | 勉強存活 |
| 陣亡 | < 0，或任一週超支率 ≥ 50% | — |

### 5.4 獎勵機制

**獎勵金 = 月正餘額合計 × 等級比例**（月正餘額合計 = 所有存活週的 R 加總，超支週不抵扣）

| 等級 | 比例 |
|---|---|
| S | 30% |
| A | 20% |
| B | 10% |
| C | 0% |
| 陣亡 | 0%，獎勵池凍結一個月 |

**分流**（預設 50／50，可調）：消費池（買公仔、遊戲，花費時記為「獎勵」分類不計入週花費）／投資池（買零股，只記金額不追股價）。

消費池可跨月累積；連續 3 個月 A 以上解鎖「Boss 獎勵」，當月可額外動用月正餘額的 10%。

**設計原則**：獎勵金永遠來自真實省下的錢，等級只決定可動用的比例。

### 5.5 成就（先做 5 個）

初次存活／四連勝／鐵人月（整月無超支）／分期終結者（任一分期繳完）／現金流大師（單月餘額率 ≥ 40%）。

### 5.6 HP 視覺

每週開始 HP = 100%，HP = 剩餘額度 ÷ 週上限。低於 20% 變色警示，歸零顯示「瀕死」，負值顯示「陣亡」但仍可記帳。這是 5.2 的視覺化，不另設規則。

## 6. 消費分類體系（本版新增）

### 6.1 業界做法調查

**記帳軟體的做法**：台灣主流做法是以食、衣、住、行、育、樂六大項為一級分類，再依個人消費習慣微調；建議一級類別控制在 5～6 項、每類子項不超過 5 個，因為分類欄目越多越容易混淆、記帳時越難決定。MOZE 的教學同樣以食衣住行育樂為最常見的大分類，並指出分類太細會瑣碎到難以歸類、太廣又不好掌握預算。另有一派在六大類之外增設「其他」承接頻率不固定的支出（稅費、勞健保、孝親費、貸款）。

**銀行的做法**：銀行走的是 **MCC（Merchant Category Code，商店行業代碼）**，由 ISO 制定、國際通用，商家申請刷卡機時登記營業類別後由銀行分配。銀行的回饋認定完全依 MCC，例如餐飲類常見認定為 5811、5812、5813、5814。

**兩套邏輯不對齊，這是關鍵發現**：
- 百貨內的餐廳若使用百貨提供的刷卡機，MCC 會變成百貨而非餐飲
- 透過 LINE Pay、街口等電子支付付款時，向銀行請款的單位變成支付公司，MCC 會跟著改變
- 外送平台（foodpanda、Uber Eats）常被排除在餐飲認定之外

**對本系統的決定**：**採記帳軟體的生活分類，不採 MCC。** 理由是本系統的目的是「理解自己的消費行為並調整」，而 MCC 反映的是商家的營業登記，不是消費者的實際意圖——在百貨美食街吃飯，行為上是「食」，MCC 上是「住／購物」。若日後要做信用卡回饋最佳化才需要 MCC，那是另一個功能。

### 6.2 本系統的分類定義

**兩層結構：一級 7 類（6 生活類 + 獎勵）、二級每類 3～5 項。**

| 一級 | 代碼 | 涵蓋 | 二級（預設）|
|---|---|---|---|
| 食 | `FOOD` | 所有入口的東西 | 三餐外食、食材採買、飲料零食、聚餐應酬 |
| 衣 | `CLOTHING` | 穿戴與個人整理 | 服飾鞋包、美容美髮、配件飾品 |
| 住 | `HOUSING` | 居住與家用 | 水電瓦斯、居家用品、修繕、通訊網路 |
| 行 | `TRANSPORT` | 移動 | 大眾運輸、油資停車、計程車與共乘、車輛保養 |
| 育 | `EDUCATION` | 學習與健康 | 書籍課程、訂閱服務、醫療保健、運動健身 |
| 樂 | `ENTERTAINMENT` | 想要而非需要 | 娛樂休閒、旅遊、3C 與嗜好、禮物人情 |
| 獎勵 | `REWARD` | 由獎勵池支出 | （不分子類）|

**「其他」刻意不設。** 業界常見的「其他」在實務上會變成垃圾桶，最後佔比最高卻分析不出東西。稅費、保險、貸款這類支出在本系統走「固定支出」而非「花費」，不需要「其他」承接；真的無法歸類的個案歸「育」或「樂」，並在備註寫明。若使用超過三個月發現確實有大量無法歸類的支出，再評估新增。

**分類屬性**（每個一級分類帶三個旗標，供第 6.4 節分析使用）：

| 屬性 | 說明 | 預設值 |
|---|---|---|
| `counts_toward_target` | 是否計入週花費 | 除 `REWARD` 外皆為 true |
| `necessity` | 必要／彈性／想要 | 食住行＝必要；衣育＝彈性；樂＝想要 |
| `benchmark_pct` | 建議佔比基準 | 見 6.3 |

`necessity` 是「想要 vs 需要」判斷的結構化版本，這是業界一致強調的思考點；本系統把它做成欄位而非靠使用者當下判斷，是為了讓分析可以自動化。

### 6.3 佔比基準（給第 6.4 分析用）

初版基準值採以下配置，**明確標示為假設值**，累積三個月資料後改以個人歷史中位數為基準：

| 一級 | 建議佔比 | 說明 |
|---|---|---|
| 食 | 30～40% | 單人外食為主的合理區間 |
| 衣 | 5～10% | |
| 住 | 10～15% | 房租走「固定支出」不在此，此處只含水電家用 |
| 行 | 10～15% | |
| 育 | 5～15% | 投資自己，超標不一定是壞事 |
| 樂 | 10～20% | |

**重要**：基準值是討論起點不是規範。分析功能的訊息措辭要避免道德評價（不要寫「你娛樂花太多」），改為陳述事實與對比（「本月樂佔 28%，高於你前三個月的 15%」）。

### 6.4 分析功能（新增需求）

**放在獨立的「分析」頁，Phase 3 隨月結一起做。**

| 分析項 | 內容 | 資料需求 |
|---|---|---|
| 分類佔比 | 本月各一級分類金額與佔比，圓餅圖 + 排序清單 | 當月 |
| 與基準對比 | 超出 `benchmark_pct` 上限的分類標記 | 當月 |
| 與自己對比 | 各分類本月 vs 前三個月平均，標出變化最大的三類 | 3 個月 |
| 必要性結構 | 必要／彈性／想要三者佔比，趨勢線 | 3 個月 |
| 超支歸因 | 超支週的花費按分類拆解，指出哪一類貢獻最多 | 當月 |
| 調整建議 | 列出「若某分類回到基準，每週可多省多少」 | 當月 |

**設計原則三條**：
1. **只陳述、不說教。** 給數字與對比，不給價值判斷。
2. **資料不足時說資料不足。** 未滿三個月時「與自己對比」顯示「需要三個月資料，目前 N 個月」，不用單月資料硬做趨勢。
3. **建議必須可行動。** 「減少娛樂支出」不算建議；「樂類回到 20% 每週可多省 NT$450，相當於每週多 3 分」才算。

Phase 5 的月結 AI 分析讀的就是這一節的輸出，不是原始流水帳。

### 6.5 自訂規則

**二級分類：完全自由**，可增刪改、可調順序、可設圖示。記帳當下的彈性都在這一層。

**一級分類：固定 7 類，但開放「有上限的自訂」**，規則如下：

| 動作 | 是否允許 | 說明 |
|---|---|---|
| 刪除內建的 7 類 | ❌ | 分析基準與歷史資料依賴它們 |
| 修改內建 7 類的顯示名稱 | ✅ | 例如把「育」改成「學習與健康」，代碼 `EDUCATION` 不變 |
| 修改 `necessity` 與 `benchmark_pct` | ✅ | 你的生活型態與預設假設不同時調整 |
| 新增自訂一級分類 | ✅ **最多 2 個** | 共 9 類上限 |
| 停用自訂一級分類 | ✅ | 只能停用不能刪除，歷史資料保留 |

**新增自訂一級分類的三個強制條件：**
1. 必須指定 `necessity`（必要／彈性／想要），否則分析的必要性結構會出現缺口
2. 必須指定 `benchmark_pct` 區間，且新增後系統重新檢查所有一級分類的基準總和是否落在 90～110%，超出範圍要提示調整
3. 新增時必須從既有分類搬移至少一個二級分類過來，不能建空的一級分類

**為什麼允許但設上限**

允許的理由：預設的 7 類是通用假設，不一定合你的生活。常見的合理自訂是「寵物」（飼料、醫療、美容原本散在食育樂三類，看不出真實成本）、「孝親與人情」（目前塞在樂類的禮物人情，但這筆錢的性質完全不同）、「投資理財」（目前走固定支出，但有人想單獨追蹤）。這些自訂會讓分析變準，不是變亂。

設上限的理由有三：
1. **分析基準會稀釋。** 佔比分析的解析度來自「類別夠少、每類夠大」。12 類時每類平均 8%，波動 2% 就看似 25% 的變化，訊號被雜訊淹沒。
2. **記帳當下的決策成本。** 業界一致建議一級 5～6 項，本系統已經 7 類。9 是在「能表達個人差異」與「選的時候不用想太久」之間的上限。
3. **歷史可比性。** 每新增一個一級分類，之前的月份就少一個維度，跨月對比要處理缺口。上限 2 個把這個問題控制在可接受範圍。

**「其他」仍然不設。** 如果你發現需要一個籃子裝雜項，那正確做法是新增一個名字明確的自訂分類（例如「寵物」「醫療」），而不是開一個叫「其他」的垃圾桶。系統應該在使用者嘗試把自訂分類命名為「其他」「雜項」「Misc」時給出提示。

**開放時機**：Phase 1 只 seed 內建 7 類與二級分類，**不做自訂 UI**；自訂一級分類的功能放 Phase 3，與分析頁一起做。理由是自訂的價值只有在看得到分析結果時才顯現——先用兩三個月內建分類，你才知道自己真正缺哪一類。

### 10.2 Phase 5 混合模型

原則：便宜、高頻、格式固定的任務給 NVIDIA NIM 託管的開源模型；需要理解脈絡的低頻任務給 Claude。

| 任務 | 頻率 | Provider |
|---|---|---|
| 自然語言記帳拆欄位（「午餐 120 刷國泰」）| 每天數次 | NVIDIA NIM |
| 花費分類建議 | 每筆 | NVIDIA NIM |
| 月結分析建議 | 每月一次 | Claude |
| 週中存活預警 | 每週一次 | NVIDIA NIM 先試 |

實作要點：
- NIM 端點 `https://integrate.api.nvidia.com/v1`，OpenAI 相容格式，用 `openai` 套件換 `base_url`
- 模型 ID 填完整字串（如 `nvidia/nemotron-3-super-120b-a12b`、`qwen/qwen2.5-72b-instruct`）
- 中文輸入任務要實測 Nemotron 與 Qwen，選準確率高者
- API key 有效期最長一年，認證失敗要回明確錯誤，不可默默退回 Claude 多花錢
- NIM 免費端點僅限個人與開發使用；開放他人使用需改付費管道
- 所有呼叫經 `services/llm/router.py`，不得直接呼叫 SDK
- 每個任務定義 Pydantic schema，兩家模型用同一 schema 驗證

### 10.3 已知待辦（尚未納入規格）

1. **帳戶餘額對帳**：只記花費不記餘額，月底不知道錢有沒有真的省下來。Phase 4 加「月底實際餘額」比對，差額提示漏記
2. **多人分帳／代付**：請客後朋友轉帳回來怎麼記。建議加「待收回」標記
3. **年度攤提**：年終、保險年繳這類非每月支出，可支配公式目前只看當月
4. **自主備份**：Railway 有備份，但建議每月自動寄一份 JSON 到信箱
5. **規則變更的公平性**：已結算月份（`reward_ledger` 有記錄）凍結，只有未結算月份用新規則

## 11. 品質與驗證

> 初版不引入獨立的 QA Agent。測試由開發端撰寫、由使用者（ABow）實際使用驗證；QA Agent 的整合留待後續版本，屆時本節會被替換為正式的 QA 流程規格。

### 11.1 誰負責什麼

| 角色 | 負責 |
|---|---|
| ABow | 實際使用、記錄體驗問題與缺陷、決定修或不修、merge |
| 規劃端 Claude | 產出測試條件；判讀 Claude Code 回報的測試結果；判斷何時該停下來修而不是往前加功能 |
| Claude Code | 撰寫並執行 Unit Test 與 API 測試、修缺陷、回報結果 |
| GitHub Actions | 每個 PR 自動跑測試，失敗擋合併 |

### 11.2 最低測試要求（不因為是個人專案而省略）

| 層 | 範圍 | 階段 |
|---|---|---|
| Unit | `week_rule`、`scoring`、`budget`、`installment` 四個核心計算 | Phase 0 起 |
| API | 每個端點的正常路徑 + 主要錯誤路徑 | Phase 1 起 |
| 負向 | 金額、日期、品項欄位的異常輸入 | Phase 1 起 |
| user_id 隔離 | 改請求的 user_id 不能讀寫別人資料 | Phase 1 起，即使只有一人使用 |
| E2E | P0 流程兩條：記一筆花費→首頁 HP 更新；月結→獎勵池寫入 | Phase 1 末 |

### 11.3 幾條不能違反的規則

- **`week_rule` 前後端必須讀同一份 `tests/fixtures/week_cases.json`**，任一邊不一致即不可合併。這是本系統最容易兩端各寫一套然後悄悄分歧的地方
- 500 錯誤與 traceback 是否外洩，只在 `DEBUG=false` 的環境驗證
- 不得為了讓 CI 綠燈而 skip 或 xfail 測試卻不寫原因
- 修改測試的預期值必須另開 commit（前綴 `test:`）並在 PR 說明寫清楚改了什麼、為什麼，防止「改預期讓它過」
- 「測過了」需要證據：測試執行輸出或 CI 連結，口頭宣告不算

### 11.4 使用者體驗記錄

ABow 在實際使用中記錄的體驗問題與缺陷，是初版最重要的品質來源——自動化測試測得出「功能對不對」，測不出「用起來想不想繼續記帳」。

建議做法：在 repo 開一個 `docs/usage-log.md`，記錄格式三欄即可（日期／情境／問題或感受）。每個 Phase 結束時由規劃端 Claude 讀這份記錄，轉成缺陷或需求變更。

**Phase 1 結束後強制連續記帳兩週再進 Phase 2**，把體驗問題在加功能之前找出來。

### 11.5 已知最高風險區（測試要重點覆蓋）

| 風險 | 說明 |
|---|---|
| 週歸屬算錯 | 回 200 但歸到錯的週 → HP 顯示正常、分數錯。這類「跑得過但業務邏輯錯」的情境最難發現 |
| 前後端週規則分歧 | 兩端各寫一套，悄悄不一致 |
| 「獎勵」被計入週花費 | 存了錢還被扣分 |
| 月週數判定 | 4 或 5 影響週上限除數 |
| 固定支出過期仍扣 | 設了結束月但仍計入可支配 |
| 時區 | 晚上 11 點半記帳存成隔天 |
| 修改月薪影響過去 | 已過去的週上限不應被改動 |
| 分類異動 | 新增或停用一級分類後，歷史月份的分析基準如何處理 |
| 自訂分類上限 | 已有 2 個自訂時再新增要被擋下，且基準總和檢查要生效 |
| **首期月推算錯誤** | 消費日 = 結帳日當天（邊界）、結帳日後一天、跨年、結帳日 31 遇 30 天月份；推算錯一個月，連續兩個月的週上限都錯且看起來合理 |
| **兩個時鐘混用** | 分期期款被同時計入週花費與可支配扣項（重複扣）；或期初卡債誤入分類分析 |
| **繳款月偏移推算** | 結帳 27／繳款 15 應為次月，結帳 1／繳款 20 應為同月；覆寫後來源欄位改動是否正確重算 |

## 12. 開發方式

- **Claude Code + VS Code**，repo 根目錄維護 `CLAUDE.md`
- 分階段開發，每個 Phase 結束更新 `CLAUDE.md` 與 ADR（`docs/adr/`）
- PR 流程，ABow 自行 review 與 merge
- 語言規範：遵循台灣技術社群用語（程式碼不說代碼、資料不說數據、品質不說質量、實作不說落地）
- Commit message：英文，Conventional Commits
